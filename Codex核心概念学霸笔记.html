Codex 核心概念速览
代理循环 × 沙箱 × 审批 × AGENTS.md × Memory / Chronicle
来源：AI 编程指南 · 02 Codex 核心概念速览 ｜ 更新 2026.06.20
01 · 先搭一张“概念地图”
代理→ 沙箱→ 审批→ 执行 / 验证
中间主角是 Agent：它在循环里工作；Sandbox 画出能动手的圈；Approval 决定出圈时要不要问你；AGENTS.md 在开工前喂项目规矩；Memory / Chronicle 帮它把经验带到后续会话。
你觉得 Codex “不肯改”或“突然停下来”，通常不是它失灵，而是某一道边界正在生效。
02 · 代理（Agent）：会自己想、做、看
代理 ≠ 聊天框
Codex 能自己拆任务、调用工具、读取结果，再决定下一步；它不只给一段文字，而是尝试把目标跑完并验证。
想：读文件 / 看报错→ 做：改代码 / 跑命令→ 看：测试 / 检查输出
例如“这个测试为什么挂了？”会变成一条代理循环：跑测试 → 读错误 → 找根因 → 修改 → 再跑一次。你给的是目标，Codex 负责在项目里往前推进。
03 · 沙箱（Sandbox）：它能动手的圈
沙箱是技术边界：限制 Codex 能改哪些文件、能不能联网。它派生出来的 git、包管理器和测试命令，也一起受这道边界约束。
read-only
只读、不联网
适合审查与出方案 workspace-write
只写工作区、默认不联网
日常开发常用 danger-full-access
全机器可写、可联网
完全信任环境才用
工作区外的桌面文件没有被改，不是 Codex 偷懒，而是它们不在围栏里。
04 · 审批（Approval）：到了边界，谁来点头
审批是策略边界：沙箱管“能不能”，审批管“问不问”。这两个旋钮要分开理解。
untrusted不在可信集合里的命令，执行前先问。
on-request默认在沙箱里做，需要出圈时才停下来问，日常最平衡。
never不弹审批，适合自动化；但权限仍由沙箱决定。
日常推荐组合
sandbox_mode = "workspace-write"
approval_policy = "on-request"
慎用：danger-full-access + never 等于扩大围栏、取消询问；只在完全信任的环境使用。
05 · AGENTS.md：项目的入职手册
把项目规矩写进 AGENTS.md，Codex 每次开工前就能读取并遵守。它应该短小、持久、跟着仓库走。
✓构建与测试命令：例如 pytest -q。
✓代码审查要求：例如改完必须跑 lint。
✓仓库约定：目录布局、命名方式、提交规则。
全局~/.codex/AGENTS.md：个人偏好，跨项目生效。
项目仓库根目录或子目录：项目 / 团队规矩，离工作目录越近越优先。
把一次性纠正写成规则，下一次会话就能继承——这就是反馈回路。
06 · Memory 与 Chronicle：记忆不是规则的替身
Memory从历史会话中提取技术栈、惯例和坑；教程注明默认关闭，可在设置或 config.toml 开启。
Chronicle实验性研究预览，用屏幕内容帮助理解你最近在做什么；教程注明仅 macOS / Pro 可用。
记忆写在本地、不是实时更新，也可能受地区限制；Chronicle 会增加配额消耗和提示注入风险。必须每次生效的团队规则，仍然写进 AGENTS.md。
敏感屏幕内容（密码、私信、客户数据）出现时，先暂停 Chronicle，再继续工作。
07 · 一分钟实验：亲眼看沙箱拦你
这个实验不依赖现成项目，目的是观察同一个“写文件”请求在两种模式下的不同结果。
# 1. 建目录并启动
mkdir -p ~/codex-demo && cd ~/codex-demo
codex

# 2. 会话内切换权限
/permissions

# 3. 查看当前状态
/status
1切到 read-only，请求创建 hello.txt。
2预期：写操作越出边界，Codex 停下来请求批准。
3切到 workspace-write，同样请求会在工作区内直接放行。
只读时被拦、可写时放行，就是“沙箱判边界 + 审批做询问”的现场演示。
08 · 五个概念，一句话带走
Codex 是戴着边界工作的能干搭档
  • Agent：在“想 → 做 → 看”的循环中自主推进。
  • Sandbox：限制能改哪里、能不能联网。
  • Approval：决定出圈时是否需要你点头。
  • AGENTS.md：把项目规矩写成持久指引。
  • Memory / Chronicle：为后续会话提供经验，但不能替代硬规则。
先画好圈，再让它跑起来
