Codex 第一个任务
从玩具项目到审 diff 验收：第一次代理任务的完整闭环
来源：AI 编程指南 · 06 跑通第一个任务 ｜ 更新 2026.06.20
01 · 第一次别拿正式项目练手
先建一个三行代码的玩具项目
正式仓库文件多、依赖杂，第一次很难看清它到底改了什么；玩具项目改砸了可以删掉重建，最适合熟悉沙箱、审批和 diff。
mkdir hello-codex
cd hello-codex

# Mac / Linux
echo 'def add(a, b):
    return a + b' > main.py
Windows PowerShell 里直接用记事本新建 main.py，粘贴同样的两行 Python。
02 · 需求越具体，结果越不跑偏
目标+ 范围+ 验收→ 可复查结果
模糊“优化一下这个函数”
具体“给 add 加类型注解，传入非数字时抛 TypeError。”
大而散“把项目重构一下”
先规划“先别动手，列重构方案，我确认后再分步修改。”
给它复现步骤、测试命令和完成标准；复杂任务拆小步，必要时先让它只输出方案。
03 · 第一个任务先“读”，不要先“改”
解释 main.py 这个文件在做什么，用新手能听懂的话说
解释型读文件、讲结构、零风险，不动内容。
修改型改现有代码，要审 diff。
生成型新建或补充文件，也要审 diff。
✓能准确说出 add 函数做什么，说明 Codex 读到了真实文件。
✓装好、登录、工作区路径都已验证，再进入修改阶段。
04 · 全篇核心：改完一定审 diff
给 main.py 里的 add 函数加上类型注解，并补充基本的错误处理
默认 Auto 档（通常是 workspace-write + on-request）下，工作区内的读、改、跑命令可能直接执行，Codex 会把改动以 diff 摊出来让你事后把关。
# 典型 diff 形态
- def add(a, b):
+ def add(a: float, b: float) -> float:
+     if not isinstance(a, (int, float)):
+         raise TypeError(...)
审 diff 只问三件事：改的是不是我要求的地方？逻辑我是否看得懂并认可？有没有删掉不该删的东西？
想要“改前先问、只分析不落盘”，主动用 /permissions 切到 read-only，或第一句明确说“先别动手，列方案”。
05 · 什么时候会弹审批？
工作区内读 / 改通常直接做，改完给 diff。
工作区内跑测试通常直接跑，不额外打断。
联网 / 出圈通常停下来问你是否同意。
改工作区外文件超出沙箱范围，需要审批。
第一次使用不要把权限调到最松；保留“出圈先问 + 事后审 diff”这道安全阀。
06 · 拒绝不是终点：同一线程里补话
发现 diff 不对，或拒绝了某个出圈请求，不需要退出重来。线程上下文还在，直接补充约束，让 Codex 换方向重做。
别引第三方库，用 Python 标准库 functools.lru_cache 实现就行
误解拒绝 = 这次任务失败，只能自己改。
实际拒绝 = 让它换个方向；同一线程多轮迭代，上下文仍然保留。
07 · Git：最硬的后悔药
git init
git add -A && git commit -m "codex 动手前的存档点"
小范围不满意回会话说“帮我退回到改之前的样子”。
整轮不要了git restore . 退回上一次 commit。
git restore . 会丢弃所有未提交的工作区改动。确认要整轮放弃时再用；要保留部分改动，就逐项处理。
动手前后各留一次检查点；git diff 是复查，git commit 是存档，git restore 是回退。
08 · CLI 五分钟跑通全流程
1建 hello-codex，写入 main.py，先 Git commit。
2一定在项目目录中启动 codex。
3先让它解释 main.py，确认读对文件。
4下修改指令，审 diff；遇到出圈动作再决定是否同意。
5退出后用 cat main.py / git diff 验收。
git diff
cat main.py
09 · 桌面 App：同一套闭环，换成图形界面
CLI跨平台，终端文本 diff，适合写代码和跑命令。
桌面 App仅 macOS / Windows，图形 review pane 更适合看长 diff、多项目并行。
共同点选项目 → 确认 Local → 先解释 → 再修改 → 审 diff → 留下或退回。
App 发第一条消息前确认选择的是 Local，避免把练习任务误送到云端。
10 · 第一个任务的最小内核
提需求 → Codex 改 → 你审 diff → 留下或退回
  • 先小后大：玩具项目比正式仓库更适合第一次练手。
  • 先读后改：先让它解释文件，确认它真的读到了代码。
  • 审 diff：检查范围、逻辑和删除内容，这是协作质量关。
  • 会话迭代：拒绝或不满意时补一句，不必重启线程。
  • Git 兜底：动手前 commit，改错可 restore；重要改动永远留检查点。
别急着同意，先看清它改了什么
以后再遇到 MCP、Skills、子代理和自动化，底层仍然是这套节奏：给清楚目标，观察执行，审查结果，必要时回退。
